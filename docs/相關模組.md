**專案模組總覽**

本文件說明本專案（`LLM`）中主要模組與檔案位置、職責說明、重要匯出與注意事項，方便開發者快速定位與維護。

**目錄（快速導覽）**

- **前端元件**: `src/components/` — UI 組件與頁面組成。
- **聊天元件**: `src/components/chat/` — 聊天專用 UI（`ChatWindow.tsx`、`InputArea.tsx`、`MessageBubble.tsx`、`PersonaSidebar.tsx` 等）。
- **UI 元件**: `src/components/ui/` — 小型 UI 元件（`PersonaBadge.tsx`、`Icon.tsx`...）。
- **服務層**: `src/services/` — 與 LLM、模擬串流、分析、demo 等相關的抽象層（`llmClient.ts`、`demoStream.ts`、`analytics.ts`、`prompts/` 等）。
- **狀態管理（Zustand）**: `src/store/` — `useChatStore.ts`（聊天邏輯、串流控制、session）、`useUIStore.ts`（UI 設定）。
- **資料**: `src/data/` — 靜態資料與預設內容（`predefinedQA.ts`、`copy.ts`、`testimonials.ts` 等）。
- **樣式**: `src/styles/` — Tailwind CSS 入口 `index.css` 等。
- **公開資源**: `public/`、`docs/` — 部署輸出與靜態資源（如 `public/assets/*` 存放 avatar 圖示）。

**一、前端元件（src/components）**

- `App.tsx` / `AppNew.tsx`

  - 職責：應用路由與頁面組裝。
  - 注意：`Router` 使用 `basename={import.meta.env.BASE_URL}` 以支援子目錄部署（例如 GitHub Pages 的 `/LLM/`）。

- `Hero.tsx`

  - 職責：首頁 hero 區塊 + CTA，CTA 使用 `CTAButton`（支援 `to` 與 `openInNewTab`，已處理 BASE_URL 組合）。

- `LiveDemo.tsx`

  - 職責：首頁互動示範（使用 GSAP + ScrollTrigger）以滾動展示示範問答。
  - CTA：導向 `/chat/`（透過 `CTAButton` 開新分頁時會自動加上 `import.meta.env.BASE_URL`）。

- `PricingPlans.tsx`、`FAQ.tsx`、`FeatureGrid.tsx`、`ContactSection.tsx` 等
  - 職責：Landing page 各區塊呈現。

**二、聊天元件（src/components/chat）**

- `ChatWindow.tsx`

  - 職責：聊天整體容器；包含側欄（`PersonaSidebar`）與右側聊天卡片；內含訊息滾動、輸入區與錯誤處理。
  - 近期調整：右側聊天卡高度改為 `h-[calc(100vh-4rem)]` 以接近整頁高度；串流預覽使用 `streamingContent` 顯示逐字預覽（MessageBubble with isStreaming）。

- `InputArea.tsx`

  - 職責：輸入欄與三個建議問題按鈕。
  - 注意：不要在此直接插入 assistant 回覆（避免重複），而是呼叫 `actions.sendMessage(...)`，store 會處理預設答案檢查與串流。

- `MessageBubble.tsx`

  - 職責：格式化使用者與助理的訊息顯示、可讀性指標、來源與史實核查區塊。

- `PersonaSidebar.tsx`、`PersonaBadge.tsx`
  - 職責：左側 persona 列表與簡短徽章顯示；avatar 解析會用 `import.meta.env.BASE_URL` 與 `public/assets` 做相對處理，避免子路徑部署的 404 問題。

**三、服務層（src/services）**

- `llmClient.ts`

  - 職責：LLM 抽象呼叫層（組裝 prompt、串流、取消、模擬回覆）；提供 `LLMClient` 類與預設 `llmClient`。
  - Mock 行為：`generateMockResponse` 會根據 prompt 關鍵字返回適切文字（方便本地測試）。

- `demoStream.ts`（若存在）

  - 職責：舊的／示範用的串流實作（保留為 demo 或 fallback）。

- `prompts/` 下（例如 `persona.qinShihuang.ts`、`safety.guardrails.ts`）

  - 職責：persona 的 system prompt、模式指示、以及安全 guardrail 檢查器。

- `analytics.ts`
  - 職責：封裝事件追蹤（CTA、demo 互動等）。

**四、狀態管理（src/store）**

- `useChatStore.ts`（Zustand）

  - 職責：聊天全域狀態（messages、isStreaming、streamingContent、sessions）、操作（sendMessage、startStreaming、updateStreamingContent、completeStreaming、retry、startNewSession 等）。
  - 實作重點：
    - `sendMessage`：建立 user message -> 更新 messages -> 啟動 streaming -> 呼叫 `simulateStreamingResponse`（或實際的 `llmClient.streamChat()`）。
    - `simulateStreamingResponse` 現在接受 `forcedResponse`（若 `predefinedQA` 有對應則傳入），以逐字串流預設 QA 回答。

- `useUIStore.ts`（Zustand）
  - 職責：UI 偏好（variant、mobile menu、theme 等）。

**五、靜態資料（src/data）**

- `predefinedQA.ts`

  - 職責：預定義的問答集（`qinShihuangQA`）、`predefinedQuestions` 列表與 `findAnswerByQuestion` / `findAnswerById` 等查找函式。
  - 使用場景：`InputArea` 的三個建議問題按鈕與 store 在 `sendMessage` 時的快速對應答案。

- `copy.ts`
  - 職責：站內文案（headline、features、hero CTA 等）。系統會提供 `getCurrentCopy(variant)` 以支援 A/B variant。

**六、public / docs / 部署相關**

- `public/assets/`：avatar、favicon、靜態圖片等，部署時會被保留於最終站台路徑（例 /LLM/assets/qin_icon.png）。
- `docs/`：經 Vite build 輸出或預設部署到 GitHub Pages 的目標資料夾，內含 `index.html` 與 assets。

注意事項：

- 當站點部署於子路徑（例如 GitHub Pages 的 `angelaliii.github.io/LLM`）時，所有內部導向與開新分頁連結必須包含 `import.meta.env.BASE_URL`。專案中已在 `Router basename`、以及 `CTAButton` 的開新分頁邏輯中處理 base-url 組合。

**七、常見開發任務與對應檔案**

- 啟動 dev server：`npm run dev`（依專案設定）。
- 生產 build：`npm run build`（會輸出到 `docs/`，專案預設為 GitHub Pages 部署格式）。
- 新增 persona：
  1. 在 `src/services/prompts/` 新增 persona 檔（範例可參考 `persona.qinShihuang.ts`）。
  2. 新增 avatar 到 `public/assets/`，在 `PersonaBadge` 使用時會以 `BASE_URL` 前綴解析。

**八、測試與驗證要點**

- Avatar 404：在瀏覽器 network 面板檢查 avatar URL 是否包含 `BASE_URL`（若缺少請檢查 `persona.avatar` 是否以斜線開頭或 `PersonaBadge` 的解析邏輯）。
- 預設 QA 重複回覆：若在 UI 上看到相同回覆兩次，請檢查是否在 `InputArea` 或其他 UI 元件同時手動插入 `completeStreaming`，目前程式已移除 UI 端的直接插入，僅由 store 處理。
- 串流逐字預覽：若要切換「逐字預覽」與「只顯示打字指示器」，請修改 `ChatWindow.tsx` 中 `isStreaming` 的渲染邏輯（目前預設會在 `isStreaming` 時顯示 `streamingContent` 的 `MessageBubble`）。

**九、待辦與改進建議（短期）**

- 把 `predefinedQA` 的匹配從「完全比對」擴充為「同義詞 / 模糊比對」，以便更彈性地命中預設答案。
- 增加單元測試：針對 `useChatStore` 的 `sendMessage`、`simulateStreamingResponse`、與 `llmClient.generateMockResponse` 寫簡單的單元測試。
- 清理未使用的元件檔案（例如舊版 `SocialProof.tsx`，若確定不再使用可刪除）。

# 資料展示與操作模組

## 系統目標

- 提供資料的可視化介面，使使用者能夠瀏覽、查詢並操作資料項目。
- 確保資料呈現的易用性與一致性，加速使用者決策和操作流程。

## 核心功能

- **資料表格展示**：以表格形式列出資料，支援分頁、排序和即時篩選，方便瀏覽大量資訊。
- **資料 CRUD 操作**：允許使用者新增、編輯、刪除資料項目，並即時更新顯示結果。
- **資料匯出**：支援將目前資料匯出為常用格式（如 CSV、Excel），方便離線分析與備份。
- **多樣視圖切換**：除表格外，可提供其他視圖（如清單或卡片模式）以符合不同使用情境。

## 技術架構

- **前端**：使用動態網頁技術（例如 AJAX）從後端擷取資料並渲染表格；採用現代前端框架優化操作體驗（如即時更新和單頁應用）。
- **後端**：提供 RESTful API 供前端存取，處理資料庫的查詢與異動請求，包含必要的業務邏輯與驗證。
- **資料庫**：設計良好的資料表和索引以儲存展示的資料，確保查詢效能；透過 SQL 等查詢語言進行資料篩選與操作。
- **快取**：對於頻繁存取的資料實施快取（如記憶體快取），減少資料庫負載並加快資料讀取。

# 動態欄位模組

## 系統目標

- 提供彈性的欄位管理機制，讓系統欄位能隨需求變化進行增減或調整，而不需修改程式碼。
- 提升系統適應力，快速支援新業務需求，減少開發維護成本。

## 核心功能

- **欄位自定義**：提供介面允許管理者為特定資料實體新增或移除自定義欄位。
- **欄位屬性設定**：可設定欄位類型（文字、數字、日期等）、預設值、選項清單及驗證規則，確保輸入資料正確性。
- **動態表單生成**：系統根據欄位設定自動生成相應的輸入表單或編輯介面，使用者無需手動開發表單。
- **系統整合**：新增加的動態欄位可立即被其他模組（如篩選器、報表）識別和使用，維持系統功能的一致性。

## 技術架構

- **欄位定義儲存**：將自定義欄位的結構與屬性儲存在資料庫的中繼資料表中（例如 Fields 設定表），系統啟動時載入配置。
- **前端動態渲染**：前端利用欄位定義動態生成表單 UI 元件，搭配驗證函式庫確保即時驗證（例如必填檢查、格式驗證）。
- **後端適應層**：後端 API 根據動態欄位配置自適應請求與資料庫操作，例如根據欄位定義構造 SQL 語句或調整資料物件結構。
- **快取與效能**：對欄位配置進行快取，以減少每次請求時的重複讀取，確保即使欄位數量增加也能維持良好效能。

# 編輯器模組

## 系統目標

- 提供所見即所得的內容編輯環境，讓使用者能輕鬆撰寫和格式化內容。
- 確保編輯器與系統其他部分無縫整合，所編輯內容能安全儲存並正確顯示。

## 核心功能

- **所見即所得編輯**：內建富文本編輯器，支援文字樣式（粗體、斜體、底線）、段落格式、列表、超連結等豐富的格式設定。
- **原始碼模式**：提供切換至 HTML 或 Markdown 原始碼編輯的功能，滿足進階使用者對內容格式的精細控制需求。
- **多媒體插入**：允許在內容中插入圖片、影片或其他媒體（依系統設定可能限制類型），並提供基礎的媒體調整選項（如縮放、置中）。
- **版本控制**：保存內容編輯的歷史版本，使用者可查看過去版本差異或恢復至先前版本，避免誤編輯造成損失。

## 技術架構

- **前端編輯器元件**：整合開源的富文本編輯器套件（例如 CKEditor、Quill），透過插件機制擴充所需功能（如表格插入、代碼區塊高亮）。
- **資料清理與安全**：後端在儲存使用者編輯內容前執行內容過濾與清理（例如移除不安全的腳本），防止 XSS 等安全問題。
- **檔案與媒體處理**：針對使用者上傳的圖片或檔案，提供後端服務儲存至檔案系統或雲存儲，並在內容中以引用連結方式呈現。
- **內容儲存**：將編輯後的內容以適當格式（HTML 或 Markdown）存入資料庫，未來展示時再根據需要轉換為前端可呈現的格式。

# 篩選器模組

## 系統目標

- 提供強大的資料篩選工具，讓使用者能夠依多種條件從大量資料中快速找到相關資訊。
- 簡化查詢過程，以直觀方式構建篩選條件，提高使用者在系統中的資料檢索效率。

## 核心功能

- **多條件篩選**：使用者可以根據不同欄位設定多個篩選條件（例如關鍵字搜尋、類別選擇、日期範圍），系統將同時套用這些條件。
- **進階查詢邏輯**：支援條件組合（AND、OR）及括號優先順序等進階查詢功能，讓使用者建立複雜的篩選邏輯。
- **即時結果更新**：當使用者調整篩選條件時，結果清單即時更新，無需重新載入頁面，提供即時的互動回饋。
- **篩選條件保存**：允許使用者將經常使用的篩選條件組合儲存為篩選方案，以便日後快速載入使用，提升重複查詢的便利性。

## 技術架構

- **篩選介面**：前端實作友善的篩選條件設定 UI，例如下拉選單、核取方塊、日期選擇器等元件，並提供動態新增/移除條件的功能。
- **查詢轉換**：前端將使用者選定的篩選條件轉換為結構化查詢請求（如 RESTful API 的查詢參數或 GraphQL 查詢），傳送至後端。
- **後端查詢引擎**：後端接收條件後生成相應的資料庫查詢語句（如 SQL 的 WHERE 子句），使用索引優化查詢效能，並將結果集返回前端。
- **快取與索引**：對常用的篩選請求結果進行快取，並在資料庫層面對篩選欄位建立索引，確保篩選操作在大量資料下仍保持快速響應。

# 報表模組

## 系統目標

- 提供豐富的資料報表生成功能，將分散的資料彙整成有意義的資訊，協助企業用戶進行分析與決策。
- 自動化產生週報、月報等定期報表，減少人工整理數據的時間，確保資訊即時性和準確性。

## 核心功能

- **報表模板設計**：管理者可以透過介面設計報表模板，選擇資料來源與欄位、定義呈現格式（如表格或圖表）和計算方式（如加總、平均）。
- **多樣圖表支援**：系統內建多種圖表類型（長條圖、折線圖、圓餅圖等）供選擇，用於視覺化展示關鍵指標和趨勢。
- **動態參數報表**：允許使用者在產生報表時輸入參數（例如日期範圍、部門選擇），據此篩選資料生成特定情境的報表。
- **報表輸出與分享**：支援將報表匯出為 PDF、Excel 等格式，並提供列印功能；可設定自動發送報表至指定電子郵件，方便分享給相關人員。

## 技術架構

- **報表生成引擎**：後端實作報表生成服務，根據選定模板從資料庫擷取資料、計算彙總指標，並將結果格式化為報表內容（如 HTML 或 PDF）。
- **圖表繪製**：前端使用圖表繪製函式庫（如 Chart.js、ECharts）將報表資料轉換為可視化圖表，或後端使用報表庫直接生成圖表影像嵌入報表。
- **任務排程**：對於定期報表，使用排程器（如 cron 工作或後端任務排程系統）在預定時間自動執行資料擷取和報表生成，確保報表按時產出。
- **權限控管**：報表模組與權限系統整合，確保只有授權的使用者可以查看或產生特定報表，保護敏感資訊。

# 頁面權限管理模組

## 系統目標

- 強化系統安全性，藉由細粒度的頁面與功能權限控制，防止未授權的存取和操作。
- 提供直觀的權限配置工具，方便管理者為不同角色設定適當的存取權限，降低維護複雜度。

## 核心功能

- **角色與使用者管理**：允許建立多種使用者角色，並將使用者分配至一個或多個角色，以套用對應的權限組合。
- **頁面權限設定**：管理者可設定每個角色對系統中各個頁面或功能的存取權（允許/禁止），例如後台管理頁僅供管理員角色使用。
- **繼承與例外**：支援權限繼承機制（如子頁面可繼承父級頁面的權限），同時允許針對特殊情況設定例外權限。
- **即時權限檢查**：當使用者嘗試存取頁面或操作功能時，系統即時檢查其角色權限，拒絕未授權的請求並提供提示。

## 技術架構

- **RBAC 模型**：採用角色為基礎的存取控制（Role-Based Access Control），在資料庫中建立使用者、角色、權限對應關係的表格，以高效查詢使用者權限。
- **前端路由保護**：在前端應用設定路由守衛（guard），根據使用者角色決定是否允許進入某些頁面；不符合權限則導向錯誤頁或登入頁。
- **後端攔截驗證**：後端在每個 API 端點實作權限驗證中介層（middleware），確保即使繞過前端，未授權請求也無法取得敏感資料或執行關鍵操作。
- **管理介面**：提供圖形化的權限管理後台，呈現角色與頁面矩陣，讓管理者直觀地查看和調整權限設定；所有權限變更操作需記錄日誌以備稽核。

# 標籤管理模組

## 系統目標

- 引入標籤（Tag）機制以靈活分類和組織資料，使使用者能以關鍵字快速標記與檢索相關項目。
- 增強資料的語意關聯性，透過標籤建立內容之間的連結，提升資訊管理和發現的效率。

## 核心功能

- **標籤建立與刪除**：使用者或管理者可以新增新標籤來描述特定主題或屬性，也可移除不再使用的標籤，保持標籤集合的整潔。
- **標籤附加**：允許將一個或多個標籤附加到各種資料項（如文章、紀錄、檔案）上，一個項目可擁有多個標籤以完整描述。
- **標籤搜尋與篩選**：支援依標籤進行資料篩選或全文搜尋，使用者可點擊標籤以查看所有被該標籤標記的項目，加速相關內容的發現。
- **標籤管理**：提供後台介面檢視所有標籤列表，包括每個標籤的使用頻率；支援標籤合併（將多個相似標籤合併為一）和重新命名，避免重複或歧義的標籤存在。

## 技術架構

- **資料模型**：在資料庫中設計標籤與資料項的多對多關聯表，確保可以有效率地查詢特定標籤下的所有項目，以及項目的所有標籤。
- **前端顯示與輸入**：提供直觀的 UI 元件，如標籤雲或自動完成功能。在項目編輯界面中，使用者輸入部分文字時即出現建議標籤清單以供選擇，或新增新標籤。
- **索引與搜尋**：對標籤名稱和關聯進行索引，優化搜尋速度；大型系統可能採用全文檢索引擎（如 Elasticsearch）加速標籤的搜尋與分析功能。
- **權限控制**：結合頁面權限模組，可設定哪些角色有新增/刪除標籤的權限，避免一般使用者任意創建過多無意義標籤。
