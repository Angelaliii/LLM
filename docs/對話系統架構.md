# 對話系統架構說明

> 文件版本: 2.2
> 最後更新: 2025-12-04

本文件說明整體資料流、前後端契約（回傳欄位）以及 V2（Archive Repair Mode）在各 Stage(S0-S5) 中的互動要點。請以此為開發規格文件來源，特別注意與 `mission` 資料結構與 `game` API 的欄位一致性。

## 核心更新（對齊 V2）
- 新增 mission 欄位: `redactedFields`, `promptHints`, `verificationRules`。
- 回傳與事件欄位: `promptChips`, `notebookCapture`, `keyPointAchieved`, `stageUnlocked`。
- 新增驗證 API 建議: `POST /api/game/verify`（S4 驗證使用）。

## S0-S5 快覽（在系統中的位置）
- S0: 任務選單（選擇歷史檔案 / mission）
- S1: 檔案解密室（視覺化殘缺欄位，`redactedFields`）
- S2: 選擇調查對象（選 NPC，載入 persona）
- S3: 深度訪談與線索收集（Guided Inquiry）
  - 顯示 `promptChips`（事實/衝突/同理）
  - 對話中觸發 `notebookCapture` 與 `keyPointAchieved`
- S4: 檔案修復（把 Notebook 卡片拖入殘缺欄位，呼叫驗證）
  - 使用 `POST /api/game/verify` 或 `/api/game/chat` 的驗證模式
- S5: 觀點驗證（Reflection / 短答或 LLM 評估回饋）

## 系統架構概覽（精簡版）

```
Frontend (SimpleChatRoom.tsx, MissionIntro, Notebook)
  ↓
Backend API (routes/game.ts)
  - POST /api/game/start
  - POST /api/game/chat
  - POST /api/game/verify   <-- S4 驗證
  ↓
Core service (gameService.ts)
  - load persona
  - load mission
  - RAG search (knowledge)
  - build system prompt
  - call LLM(s)
  - detect key points / stage unlock
  - return response with V2 fields
```

## API 回傳契約（關鍵欄位，前端必須消化）

`POST /api/game/start` 回傳（建議）:
- `sessionId`, `missionId`, `npcId`, `redactedFieldsStatus`

`POST /api/game/chat` 回傳格式（主要欄位）:
{
  responses: [...],
  knowledgeUsed: [...],
  promptChips?: [{ id, text, type }],
  stageUnlocked?: string,
  keyPointAchieved?: { id, title, summary, sourceId },
  notebookCapture?: { id, text, sourceId }
}

`POST /api/game/verify`（建議）:
- request: `{ sessionId, stageId, notebookCardIds }`
- response: `{ verified: boolean, explain?: string, stageUnlocked?: string, keyPointAchieved?: {...} }`

> 注意: 後端在任一回覆中若包含 `notebookCapture` 或 `keyPointAchieved`，前端應自動把該卡加入 Notebook；若包含 `stageUnlocked`，前端應更新 mission store 並顯示 `StageCompletionCard`。

## 詳細處理流程（gameService 處理步驟，含 V2 延伸）

1) 載入 PERSONA
  - 檔案: `backend/data/persona/*.md`
  - 含語氣、知識範圍、回答規則

2) 載入 Mission 資料
  - 檔案: `backend/data/missions/*.ts`
  - 必要欄位: `redactedFields`（S1 欄位）、`promptHints`、`verificationRules`

3) RAG 檢索 Knowledge Base
  - 搜尋與 message 相關的 knowledge，回傳 `knowledgeUsed`

4) 建構 System Prompt
  - 結合 persona、mission、ragKnowledge
  - 若 mission 指定 `redactedFields`，在 system prompt 中加入修復目標描述（用於 S3 引導）

5) 呼叫 LLM(s)
  - 兩組溫度（0.7、0.9）或根據需求調整

6) 檢測關鍵事件
  - `checkKeyPointAchieved(message, mission)` → 回傳 `keyPointAchieved` + `notebookCapture`
  - `checkStageUnlock(...)` → 回傳 `stageUnlocked`

7) 組成回傳物件
  - 含 `responses`, `knowledgeUsed`, 可選 `promptChips`, `notebookCapture`, `keyPointAchieved`, `stageUnlocked`

## V2 資料欄位對照（開發注意）
- `mission.redactedFields` : [{ id, label, hint, linkedKnowledgeIds }]
- `mission.promptHints` : [string]（初始化 prompt chips，可被後端覆寫）
- `response.promptChips` : 用於 S3 顯示的三個追問候選
- `response.notebookCapture` : 前端自動加入 Notebook 的證據卡
- `response.keyPointAchieved` : 代表系統判定的關鍵證據
- `response.stageUnlocked` : 完成某 stage 或解鎖下一階段

## ASCII 流程圖（S0 → S5）

```
S0: 任務選單
  ↓
S1: 檔案解密室 (redactedFields)
  ↓ (選 NPC)
S2: 選擇證人 (load persona)
  ↓
S3: 深度訪談 (promptChips shown, notebookCapture)
  → backend returns notebookCapture / keyPointAchieved
  ↓
S4: 檔案修復 (拖拉卡片 -> POST /api/game/verify)
  → verify returns { verified, stageUnlocked }
  ↓
S5: 觀點驗證 (reflection / LLM 評估)
```

## 開發注意事項與建議
- 前端必須處理 `promptChips`, `notebookCapture`, `stageUnlocked` 這三個欄位。
- `notebookCapture` 應包含 `sourceId` 以便前端顯示 Knowledge Snippet 的來源。
- 驗證策略建議先以 keyword 驗證實作，再視成本加入 LLM 驗證。
- 建議在 `routes/game.ts` 新增 `/verify` endpoint，並在 `gameService` 中加入 `verifyStage` 函式。

### 5. Backend 核心處理 (最關鍵!)

```typescript
// backend/services/gameService.ts

export async function handleGameChat(request: GameChatRequest) {
  const { npcId, message, conversationHistory } = request;
  
  // === 處理流程 ===
  
  // 步驟 1: 載入 NPC PERSONA 檔案
  const npcPersona = loadNPCPersona(npcId);
  // 讀取: backend/data/persona/NPC_JP01_Student.md
  // 包含: 角色個性、語氣、知識範圍、回答規則
  
  // 步驟 2: 載入 Mission 資料
  const missionData = getMissionById('E2');
  // 讀取: backend/data/missions/mission.ts
  // 包含: 任務背景、NPC 知識範圍、關鍵字
  
  // 步驟 3: RAG 檢索 Knowledge Base
  const knowledgeResults = await searchKnowledge(message, {
    npcRole: npcInfo.role,
    topK: 3,
    minSimilarity: 0.5
  });
  // 搜尋: backend/data/knowledge/knowledge_base.json
  // 使用向量相似度搜尋相關歷史知識
  
  // 步驟 4: 語氣轉換
  const ragKnowledge = convertRAGToRoleTone(knowledgeResults, npcId);
  // 將正式的歷史知識轉換為角色口吻
  // 例如: "總督府實施保甲制度" → 小清: "警察大人叫我們十戶組成一甲"
  
  // 步驟 5: 建構 System Prompt
  const systemPrompt = `
    # 你的角色身份
    ${npcPersona}
    
    # 任務背景資訊
    ${missionData.chunks.map(c => c.text).join('\n')}
    
    # 歷史背景參考 (已轉換為你的口吻)
    ${ragKnowledge}
    
    # 回答規則
    - 只能回答你知識範圍內的問題: ${npcConfig.knowledge.canAnswer}
    - 不能回答: ${npcConfig.knowledge.cannotAnswer}
    - 語氣: ${npcConfig.language.tone}
    - 最大字數: ${npcConfig.language.maxResponseLength}
  `;
  
  // 步驟 6: 呼叫 LLM
  const messages = [
    { role: 'system', content: systemPrompt },
    ...conversationHistory,
    { role: 'user', content: message }
  ];
  
  const [responseA, responseB] = await Promise.all([
    chatWithMistral(messages, { temperature: 0.7 }),
    chatWithMistral(messages, { temperature: 0.9 })
  ]);
  
  // 步驟 7: 品質檢查
  const qualityCheckA = checkResponseQuality(responseA, npcId);
  // 檢查: 是否包含自我介紹、教學口吻、現代詞彙等
  
  // 步驟 8: 返回結果
  return {
    responses: [
      { id: 'response_a', content: responseA, temperature: 0.7 },
      { id: 'response_b', content: responseB, temperature: 0.9 }
    ],
    knowledgeUsed  // 供前端顯示使用了哪些知識
  };
}
```

## 🎯 建議的使用流程

1. **啟動應用** → 系統自動預載入 mission 和 knowledge_base
2. **選擇角色** → 系統載入對應 PERSONA 檔案
3. **開始對話** → 系統根據角色設定回答:
   - 使用 PERSONA 中的語氣和個性
   - 從 mission 中獲取劇本背景
   - 透過 RAG 從 knowledge_base 搜尋相關知識
   - 結合以上生成符合角色設定的回答
