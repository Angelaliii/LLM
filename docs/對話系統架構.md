# 對話系統架構（以現行程式行為為準）

> 文件版本: 3.0
> 最後更新: 2025-12-25

本文件以「目前程式已實作的行為」為準，說明前後端資料流、API 契約（回傳欄位）與關鍵模組責任分工；同時把 V2（Archive Repair Mode）中尚未落地的欄位與端點集中列為「規劃中」。

---

## 系統組成與責任

### Frontend（React + Zustand）

- `frontend/app/services/llmClient.ts`：前端對話 wrapper
  - 建立/快取 `sessionId`（依 NPC 分開快取）
  - 呼叫後端 `/api/game/chat`
  - 以「逐字延遲」模擬串流 UI（後端實際回傳是 JSON）
  - 若收到 `keyPointAchieved`，會呼叫 `window.handleKeyPointAchieved(...)`
- `frontend/app/components/chat/ChatWindow.tsx`：對話 UI
  - 掛載 `window.handleKeyPointAchieved` 以顯示「關鍵點達成」提示
- `frontend/app/store/useChatStore.ts` / `frontend/app/store/useMultiChatStore.ts`：對話/導航狀態（依頁面使用而定）
- `frontend/app/components/s4/S4_ArchiveRepair.tsx`：S4 檔案修復 UI（拖拉線索、進度 100% 自動進 S5）

### Backend（Express + TypeScript）

- `backend/index.ts`：伺服器啟動
  - 啟動時預載入 mission、初始化向量資料庫（RAG）
  - 掛載路由：`/api/game`, `/api/missions`, `/api/eval`, `/api/ollama`
- `backend/routes/game.ts`：遊戲 API
  - 以記憶體 `Map` 管理 session（非 Redis）
- `backend/services/gameService.ts`：核心對話處理
  - Persona + RAG + Mission 組 prompt
  - 呼叫 LLM（目前使用 `chatWithMistral`）
  - 品質檢查 + 回退策略
  - 解析 `<suggestions>` 搭便車的追問建議
  - 檢測 `keyPointAchieved` 與 `stageUnlocked`
- `backend/services/simpleVectorDB.ts`：RAG 向量檢索（含 cache）
- `backend/services/personaCache.ts`：persona 快取

## 主要資料流（Start → Chat）

```
使用者在前端選 NPC / 任務
  ↓
POST /api/game/start { missionId, npcId }
  → 回傳 sessionId（前端依 npcId 快取）
  ↓
POST /api/game/chat { sessionId, message, summaries?, keyPoints? }
  ↓
backend/services/gameService.ts
  - filterConversationHistory
  - buildSystemPrompt(persona + player_persona + mission + RAG + memory)
  - chatWithMistral(兩組溫度)
  - parse/quality fallback
  - clean tags + extract suggestions
  - checkKeyPointAchieved + checkStageUnlock
  ↓
回傳 JSON（前端以逐字延遲模擬串流顯示）
```

## Backend API 一覽（現況）

### 1) 遊戲/對話（`/api/game/*`）

- `GET /api/game/stories`：列出故事 JSON
- `POST /api/game/start`：建立 session（必填：`missionId`, `npcId`）
- `POST /api/game/chat`：對話主端點（必填：`sessionId`, `message`）
- `POST /api/game/feedback`：記錄玩家選擇（`sessionId`, `responseId`, `selectedId`）
- `GET /api/game/session/:sessionId`：取得 session 基本資訊（回合數、時長等）
- `POST /api/game/summarize`：濃縮對話（用於 summaries / keyPoints 管理）
- `GET /api/game/persona/:npcId`：讀取 persona（可關閉/可要求 token）

### 2) 健康檢查（`/api/*`）

- `GET /api/health`
- `GET /api/test`

## API 契約（現況）

### POST /api/game/start

Request

```json
{ "missionId": "e2-industrial-agri", "npcId": "student" }
```

Response

```json
{ "success": true, "data": { "sessionId": "session-...", "missionId": "...", "npcId": "...", "message": "..." } }
```

### POST /api/game/chat

Request（現況前端通常只送 `sessionId` 與 `message`）

```json
{ "sessionId": "session-...", "message": "...", "summaries": [], "keyPoints": [] }
```

Response（核心欄位）

```json
{
  "success": true,
  "data": {
    "responseId": "resp-...",
    "responses": [
      { "id": "response_a", "content": "...", "temperature": 0.7, "qualityScore": 0.8 },
      { "id": "response_b", "content": "...", "temperature": 0.9, "qualityScore": 0.6 }
    ],
    "suggestions": [ { "text": "...", "type": "fact" } ],
    "knowledgeUsed": [ { "id": "...", "text": "...", "similarity": 0.7 } ],
    "hint": "...",
    "keyPointAchieved": { "id": "kp1", "title": "...", "description": "..." },
    "stageUnlocked": "S4",
    "gameCompleted": false
  }
}
```

## 關鍵事件與狀態（現況）

### 1) keyPointAchieved

- 後端在每次回覆後檢查「玩家輸入 + NPC 回覆」是否命中必備詞
- 命中後回傳：`{ id, title, description }`
- 前端會用 `window.handleKeyPointAchieved` 顯示提示（目前主要是 UI 提示用途）

### 2) stageUnlocked

- 後端目前的規則是：累積 2 個關鍵點後回傳 `stageUnlocked: 'S4'`
- 但此規則依賴請求中的 `keyPoints` 能「累積」；現況前端未回傳 keyPoints，因此 `stageUnlocked` 不保證穩定觸發
- 前端目前也沒有消化 `stageUnlocked` 來自動切換關卡

---

## 前端目前如何「顯示串流」

後端回傳的是 JSON（一次回來），前端在 `llmClient.ts` 內把 `responses[0].content` 拆成字元，加入小延遲逐字輸出，用來模擬打字串流效果。

## 已知落差/技術債（現況）

1) **MissionId 未完全串接**
   - `/api/game/start` 會保存 missionId，但 `gameService.ts` 目前固定使用 `getMissionById('E2')` 建 prompt
   - 因此「前端選的 mission」不一定會影響後端 prompt

2) **keyPoints/summaries 未形成閉環**
   - 後端支援在 `/api/game/chat` 接收 `summaries` 與 `keyPoints` 並寫入 session
   - 但前端目前不回傳它們，且後端也不會把新拿到的 keyPoint 自動存回 session

3) **stageUnlocked 未被前端採用**
   - 現況 S3→S4 的進入更像是「前端流程/評估」在控制
