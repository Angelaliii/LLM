## 執行摘要（≤180 字）

本專案打造一個面向國中歷史教學的互動式對話平台。前端採用 React + Vite + TypeScript，並以 `src/services/llmClient.ts` 作為可替換的模型呼叫層；系統支援教學、快問快答與 Socratic 三種互動模式，並以安全守則防止不當內容與杜撰來源，讓學生在課堂與自主學習場域能得到具可驗證性與教學導向的回覆。

## 二、問題與痛點分析

1. 教育現場現況：

   - 數位教材與互動教學需求增加，國中生希望整合能即時互動的學習工具以提高學習參與度。現行通用 LLM（例如學校個人測試使用的聊天模型）能快速生成文字，但常見問題包括語氣不穩、史實不精準與缺乏教學導向。專案中 `src/services/demoStream.ts` 提供的模擬串流能作為教學示範。

2. 國中生學習痛點（具體案例）：

   - 教師：在備課時需手動編輯模型回覆以刪除不適當或錯誤資訊，耗時且不易保證一致性；缺乏快速匯出教材格式（如講義、測驗題）。現有專案提供 `src/services/prompts/` 與 few-shot 範本機制，但缺乏教師面板與匯出功能為短板。
   - 學生：在個別練習時，模型常使用現代用語或過度簡化歷史脈絡，導致誤解；學生也缺少被引導思考的互動問題（Socratic 引導）。專案中 `src/components/chat/InputArea.tsx` 與 `ChatWindow.tsx` 可提供互動界面，但需補強提問建議與難度分級。

3. 政策與教育趨勢：
   - 各級教育強調 AI 素養與探究式學習。系統需遵守教育倫理（不美化暴力、不做現代政治宣傳）、保護未成年（不收集敏感個資），並在回答中標註史料不確定性。`src/services/safety.guardrails.ts` 應與前端敏感詞管理介面整合以落實這些要求。

## 三、機會與目標市場

1. 目標使用者（分層）：

   - 教師（首要）：國中與高中歷史教師、教學設計者。需求包括課堂即時互動工具、教材產出協助（講義、練習題）、以及能調整史實嚴謹度與回覆長度的控制面板。
   - 學生（次要）：以國中、高中學生為主，重視互動性、閱讀難度控制與思辨引導（Socratic 問題）。
   - 校內行政/教材維護者（輔助）：負責人物配置管理、敏感詞庫維護與對話資料匯出。

2. 應用場域（場景示例、與專案對照）：

   - 課堂投影互動：教師以投影呈現 `ChatWindow`，在全班提問並即時展示模型回覆，教師可在 `Controls` 中即時調整嚴謹度、模式與回覆長度以配合教學節奏（專案檔案：`src/components/ChatWindow.tsx`、`Controls.tsx`）。
   - 自主學習：學生在個別裝置以 `InputArea.tsx` 提問，系統提供「提問建議」與難度分級選單，並在回覆中標註史料不確定性（專案檔案：`src/components/chat/InputArea.tsx`、`src/utils/text.ts`）。
   - 教師備課與教材匯出：教師使用 few-shot 編輯器產出多版本答案（教學版、概覽版）、並匯出為講義或測驗題（專案需新增匯出模組與 UI）。
   - 評量輔助與回饋：系統支援教師對抽樣問答進行人工評分（10 則抽樣），分數回饋至少量版本化 few-shot 以提升模型行為一致性（需新增後端或本地版本化機制）。

3. 市場與採用策略（可行性與保守估計）：

   - 市場位置：專案屬於教育科技（EdTech）與 AI 教學工具交叉領域，目標先集中在有數位教學需求的大型縣市與實驗學校做小規模試點（pilot）。
   - 採用策略：提供教師友好的試用流程（含教案範本、few-shot 範例庫與簡易上線說明），並與校內教研團隊合作進行 2–4 週的教學試用，收集教師評分與回饋，快速迭代 few-shot 與安全守則。
   - 商業化思路（非確定）：可採訂閱式（學校或區域）、或以教材合作與教師培訓作為切入點；短期優先以免費試點與師資培訓取得使用者反饋。

4. 指標與成功條件（與第三章相關的可執行指標）：
   - 試點採用率：在 2–4 週試點中，目標教師每天至少使用系統 3 次以上完成互動教學。
   - 教師滿意度：試點後教師對「史實一致性」與「教學適用性」的平均評分 ≥4（1–5 分）。
   - 技術指標：在教室網路環境下，回覆串流啟動時間 <1s（視網路情況而定），完整回覆延遲平均 <3s（串流前提）。

說明：上述場景與指標均以現有專案可用元件為基礎（`src/components/`、`src/services/demoStream.ts`、`src/services/llmClient.ts`），並提出需要補強的功能（教師匯出、評分回饋、錨點知識庫）作為後續開發優先項。

## 四、競品與差異分析

1. 競品概覽（代表性服務，非列舉全部）：

   - 泛用對話式 LLM 服務（如大型公開聊天模型平台）：優勢在於強大的語言生成能力與即時性，但缺乏針對教學情境的結構化 prompt 與教師控制面板。
   - 教育專用平台／工具（包含部分教育科技公司推出的智能助教）：通常結合學習管理系統（LMS），但在「歷史人物角色化」與史料嚴謹性上較少專門優化。
   - 開源/研究型對話範例（學術或示範專案）：靈活且易整合，但往往缺乏生產級的安全守則與教師友好的 UI。

2. 我們的差異化價值（核心對比）：

   - 人物化 + 教學可控性：以「歷史人物人格化」作為教學載體，並把「嚴謹度」、「回覆長度」與「模式（教學/快問/Socratic）」暴露給教師操作，這在通用 LLM 與多數教育工具中並不常見。
   - 史實注記與錨點檢核：設計以錨點（時間／地點／人物）作為自動檢核步驟，並在回覆中標註史料不確定性，便於教師快速驗證與教學引用。
   - 可編輯 few-shot 與教師面板：教師能直接在 UI 編輯 few-shot 範例，並把改良後範本匯出（或匯入），這降低 prompt-engineering 門檻。
   - 教育導向的安全守則：內建拒答模板與敏感詞管理，且在遇到爭議史觀時強制多源視角呈現，減少不當內容風險。

3. SWOT（針對本專案）

   - Strengths（優勢）：
     • 教學導向的 prompt 設計與 few-shot 編輯；
     • 前端已有可替換 LLM 層（`llmClient.ts`）與模擬串流（`demoStream.ts`），便於 POC 與示範；
     • 明確的安全守則與教育倫理設計。

   - Weaknesses（劣勢）：
     • 目前缺乏正式的史實錨點知識庫（需建置或整合）；
     • 教師評分回饋與匯出功能尚未實作；
     • 若依賴商業 LLM，成本與 API 管理需提前規劃。

   - Opportunities（機會）：
     • 與學校教研單位合作做試點，能快速獲得教學反饋；
     • 擴展到其他人物與領域（文學、哲學）具有市場延展性；
     • 可結合教材供應商或出版社合作，作為互動教學補充素材。

   - Threats（威脅）：
     • 現成大型模型的迭代速度快，若無持續優化 prompt 與知識庫，可能被更強大的泛用服務部分替代；
     • 教育場域對資料與倫理要求嚴格，若出現史實錯誤或敏感事件處理不當，將對採用造成阻礙。

4. 結論（差異化戰略建議）：

   - 優先建立「錨點檢核」與「教師回饋機制」，把這兩項作為與競品最明顯的差異化賣點；同時在 POC 與試點階段強化教師入門體驗（範例庫、簡易匯出），快速收集可操作的教師評分資料以驅動後續優化。

   ## 五、產品願景與量化指標

   1. 產品願景（具體化）：

      - 成為教師可控的歷史教學助手，輸出同時具備可讀性、史實嚴謹性與適齡性的回覆；教師能以滑桿或設定快速控制「嚴謹度」「語氣」「回覆長度」，並可匯出為講義或評量材料。

   2. 量化指標與檢核口徑（操作化步驟）：

      - 回覆可讀性（教學/快問快答）：
        • 指標：回覆字數範圍與中文可讀性估算。
        • 檢核口徑：每次測試抽樣 100 則回覆；計算教學模式回覆字數落在 300–600 字比例 ≥85%；快問快答回覆落在 80–160 字比例 ≥90%。可讀性以 `src/utils/text.ts` 實作之中文指標（例如：平均句子長度、段落密度）或自訂量表，目標為大多數回覆對應年級閱讀能力。

      - 史實一致性：
        • 指標：教師評分與自動錨點檢核。
        • 檢核口徑：隨機抽樣 10 則問答，由至少 3 位有教學經驗的教師以 1–5 分評分（評分面向：史料正確性、史料脈絡呈現、拒答/標註爭議處理）。目標平均 ≥4。自動化檢核則比對回覆中提到的時間/地點/人物與本地錨點字典，至少比對 3 個錨點，若不一致則標記供教師復核。

      - 安全與合規（敏感請求攔截率）：
        • 指標：被系統攔截或轉為教學性回應的敏感/不當請求比例。
        • 檢核口徑：模擬測試集含 500 筆潛在敏感或不當請求（含暴力美化、現代政治宣傳、未成年不當內容），系統應以安全守則攔截或用教學中立替代回覆 ≥95% 的場景。

      - 前端表現（效能）：
        • 指標：首次載入時間、串流啟動延遲、完整回覆延遲。
        • 檢核口徑：在標準教室網路模擬下（或實驗網路），測 50 次互動，目標：首次載入 <2.5s（cold load），串流首段到達時間 <1.0s，完整回覆平均延遲 <3s（串流呈現下衡量）。若使用第三方 API，需同時記錄網路與 API 時延以區分瓶頸。

      - 可擴充性：
        • 指標：新增人物所需時間。
        • 檢核口徑：從建立 persona 配置（JSON/TS）、上傳 few-shot 到前端人物列表，完成最小上線（含 UI 切換）的時間 ≤15 分鐘（測試由熟悉系統的開發人員執行，備有範本）。

   3. 轉換為開發任務（短期可驗證的交付）：

      - A. 建立 `data/anchors.sample.json`（錨點字典）與 `services/anchorChecker.ts`，實現簡單的時間/地點/人物比對與標註流程。
      - B. 在 `src/utils/text.ts` 增加中文可讀性檢核函式（句長、段落密度、字數統計），並在 QA pipeline 中加入自動報表輸出。
      - C. 設計一鍵抽樣檢核腳本（Node.js）用於自動化測試：產生 100 條回覆樣本、跑可讀性/錨點/敏感詞檢核並生成 CSV 報表以便教師審閱。

   4. 評分標準示例（教師評分表格欄位，供 UI 使用）：
      - 問題 ID | 回覆摘要 | 史料正確性（1–5）| 史料脈絡完整性（1–5）| 適齡性（1–5）| 建議修正（文字欄）

   說明：以上量化指標以現有專案架構可逐步落地；短期以本地 JSON 與 script 驗證，長期再與教師面板與自動化 CI/CD 整合。

   ## 六、系統設計與使用情境

   1. 高階流程概述（事件流程）

      - 使用者輸入（`InputArea.tsx`）：學生或教師在輸入欄輸入問題，或從建議問題清單選擇題目。按下送出時觸發前端事件。
      - 前端預檢（安全/格式檢查）：在送出前由 `safety.guardrails.ts`（或對應 client-side wrapper）做敏感詞過濾與格式化；若命中敏感規則，回饋給使用者並提供替代教學性回覆選項。
      - Prompt 組裝（`llmClient.ts` 的上層）：根據 UI 設定（模式、嚴謹度、回覆長度、persona 配置），組裝系統提示詞 + few-shot + 使用者問題與 metadata（年級、語言、是否為投影模式）。
      - LLM 呼叫（抽象層 `llmClient.ts`）：呼叫模型（串流或非串流），處理 timeout、重試與錯誤回填，並回傳逐段或整段回覆。
      - 串流解析與 UI 呈現（`ChatWindow.tsx` / `MessageBubble.tsx`）：逐段渲染回覆並同步更新 token/進度指示；支援 mid-stream cancel 與重送功能。
      - 後處理（自動錨點檢核與來源摘要）：對已生成段落進行錨點抽取（時間/地點/人物），比對 `data/anchors.json`，並將比對結果顯示為「來源脈絡摘要」供教師審核。

   2. 詳細狀態流（前端 state 與事件）

      - State（`useChatStore.ts`）：
        • messages: Message[]（包含 user/system/assistant, metadata, timestamps）
        • ui: { mode, personaId, rigorLevel, lengthPref, language }
        • streaming: { isStreaming, currentMessageId, tokensReceived }
        • anchorsCheck: { status, findings }
        • errors: { lastError }

      - 事件（examples）：
        • onSubmit(question):
        - set messages append user message
        - run preCheck(question)
        - if allowed -> assemblePrompt(ui, question) -> llmClient.stream(prompt)
        - on stream chunk -> append/patch assistant message, update tokens
        - on stream end -> run anchorChecker on final text, set anchorsCheck findings
          • onCancelStream(): call llmClient.cancel(), set streaming false
          • onRetry(messageId): re-run assemblePrompt with same metadata but optionally stricter rigorLevel

   3. UI/UX 要點（課堂 vs 自主學習差異）

      - 課堂（投影）模式：默認較高嚴謹度、較長回覆（教學模式）；顯示來源脈絡摘要與教師快速編輯按鈕（快速把回覆轉為講義）；禁用直接顯示敏感詞的原文。
      - 自主學習（學生）模式：提供問題建議、難度分級（國中/高中），回覆精簡且以教學引導（Socratic）附帶延伸問題；顯示「請向教師核對」提示。

   4. 可替換 LLM 層的合約（簡要 contract）

      - 輸入：PromptPayload { systemPrompt, fewShot[], userMessage, meta: { mode, rigor, maxTokens, language } }
      - 輸出（串流模式）：Stream of { chunkText, isFinal?, tokens, tokenOffsets }
      - 錯誤模式：timeout、rateLimit、badResponse（非文字/空回覆）— 每種錯誤應被轉為具體的 UI 提示與可重試按鈕。

   5. 無障礙與國際化（實作要點）

      - 鍵盤導覽：確保 `InputArea`、送出按鈕、模式切換、人物下拉等 UI 元件都有 logical tab order 與可見 focus 樣式。
      - ARIA：訊息列表使用 `role="log"` / `aria-live="polite"`（或更適合的 live region）以支援螢幕朗讀；每個 `MessageBubble` 加上 `aria-label` 描述（說話者、摘要）。
      - i18n 支援：將文字抽離到 `src/i18n/*`，預設支持繁中/簡中/英文；提示詞會根據 `ui.language` 轉換（必要時保留 persona 語境但切換顯示語言）。

   6. 錯誤處理與可觀測性

      - 前端應顯示可理解錯誤訊息並提供重試按鈕（若為 API 錯誤則顯示建議操作）。
      - logging：在 `llmClient.ts` 記錄請求 ID、prompt 摘要、回應延遲、錯誤類型（勿記錄完整 prompt 以避免洩密），送到前端 telemetry 或後端審計管線。

   7. 小型 sequence ASCII（示意）
      User -> InputArea -> preCheck -> llmClient (stream) -> ChatWindow (render chunks) -> anchorChecker -> UI shows anchors

   說明：以上設計基於現有檔案（`src/components/ChatWindow.tsx`、`InputArea.tsx`、`src/services/llmClient.ts`、`src/services/demoStream.ts`、`src/store/useChatStore.ts`），並把可驗證步驟（錨點檢核／敏感詞攔截）放在回覆流程中，便於教師審核與自動化測試。

   ## 七、教學設計與學習成效評估

   1. 教學設計理念與學習目標

      - 理念：採用探究式學習與建構主義，透過與「秦始皇」對話把抽象史實轉為具體情境，並透過引導問題促成學生的史料比對與批判性思維。
      - 學習目標（範例）：
        • 知識：能描述秦統一後的三項主要改革（郡縣制、度量衡、書同文）。
        • 技能：能從對話回覆中擷取並比對至少兩項史料錨點（時間、地點、人物）。
        • 態度：能描述史料不確定性的性質，並以中立角度提出延伸探究問題。

   2. 範例課程設計（45 分鐘單元）

      - 導入（5 分）：教師簡述今日主題並提出一到兩個開放性問題。
      - 問題收集（5 分）：學生以小組整理問題並透過 `QuestionSelector.tsx` 提交。
      - 互動提問（20 分）：教師在投影模式下與秦始皇互動（教學模式、嚴謹度：嚴謹），學生記錄回覆的史料錨點與任何標註的爭議。
      - 分組分析（10 分）：小組比較回覆與既有教材或講義，使用 anchorChecker 標示不一致處並準備一分鐘報告。
      - 彙整與延伸（5 分）：教師總結並布置 200–400 字的延伸作業（作為評量之一）。

   3. 教師與學生測試腳本（可立即執行的驗收腳本）

      - 教師檢核流程：
        1. 設定投影模式、persona=`qin-shihuang`、模式=`教學`、嚴謹度=`嚴謹`。
        2. 提出問題："你如何評價焚書坑儒的史料證據？"
        3. 驗收點：回覆先答核心要點、標示史料類型、若有爭議則標記並列出代表觀點。使用 anchorChecker 檢核回覆中的錨點是否與本地 anchors 相符。
      - 學生檢核流程：
        1. 切換到學生模式、難度=`國中`、模式=`Socratic`，問："度量衡統一為何改變商旅活動？"
        2. 驗收點：回覆以引導問題結尾；字數在 80–160 範圍；語句簡潔適齡。

   4. 評量表與量表（建議供 UI 與教師使用）

      - 欄位：問題 ID | 回覆摘要 | 史料正確性（1–5）| 脈絡完整性（1–5）| 適齡性（1–5）| 引導性/延伸問題（1–5）| 建議修正（文字）

   5. 自動化驗證與測試計畫（工程化步驟）

      - 單元測試範例：
        • promptBuilder.spec.ts：針對不同 mode/rigor/grade 組裝 prompt，assert 包含必要 metadata 與 few-shot 標記。
        • anchorChecker.spec.ts：給定 sample 回覆與 `data/anchors.sample.json`，assert 找到/未找到的錨點符合預期。

      - 整合測試：
        • run-demo-e2e.js（Node script）：使用 `demoStream.ts` 產生 N 筆對話樣本，自動執行可讀性檢查、錨點檢核、敏感詞過濾，匯出 CSV 報表供教師抽樣審核。

   6. A/B 與量化驗證設計

      - 變數：溫度/嚴謹度/回覆長度三因子交叉（簡化為 3×3 設置以降低複雜度）。
      - 指標：教師史實一致性評分、學生小測（5 題）平均分、課堂互動率（發問次數/學生數）。
      - 執行方法：在 4–6 個班級中分組實驗，執行 4 週並採用同一套題目做前後測比較。

   7. 短期交付物（最小可驗證成果）
      - 範例教案與 few-shot 範本庫（JSON/TS）
      - `data/anchors.sample.json` 與 `services/anchorChecker.ts` POC
      - `scripts/run-demo-e2e.js` 自動化抽樣檢核與報表產生

   說明：第七章強調可操作的教學流程與工程驗證路徑；下一步可把測試腳本與 POC code 加入 repo（若您同意，我會開始建立 `data/anchors.sample.json`、`services/anchorChecker.ts` 與 `scripts/run-demo-e2e.js`）。

## 四、產品願景與成功量化指標

願景：將 LLM 化為「可控、可驗證、可教學化」的歷史對話助手，使教師能在課堂上引導學生以探究式問題深化史料理解。

- 效能：首次載入 < 2.5s；單輪回覆延遲目標 < 3s（串流呈現）。

## 九、提示詞工程要點（系統提示與安全守則）

（以下文本直接採自 `程式建構書.md` 要求，供實作時置入 `src/services/prompts/persona.qinShihuang.ts` 與 `safety.guardrails.ts`）

## 系統提示詞（秦始皇，示例）

你是「秦始皇」，以第一人稱回答，語氣與用詞應符合戰國末—秦代上層統治者的歷史語境：莊重、具權威但不俚俗。回覆應先給出精煉答案（核心要點），接著補充脈絡。遇到史料不確定或後世有爭議之處，請明確標記：「後世記載不一」或「史料欠缺」，並給出至少兩種代表性觀點（若適用，標註主流度或證據力）。

## 安全守則（摘要，示例）

- 拒絕任何美化暴力、侵略或鼓吹種族優越的要求。如遇此類請求，轉為歷史反思：描述事件的史實、當時的社會/制度原因、以及現代倫理角度的反思。
- 禁止捏造具體未存在的文獻或 URL；若引用來源，僅描述來源類型（例如《史記》、里耶秦簡、出土簡牘、近代學者研究），不提供虛構細節。
- 若使用者要求現代政治利用或宣傳，直接拒絕並提供中立、教學性的替代問題或討論方向。

## Few-shot 正例（示例，請同步寫入 `persona.qinShihuang.ts`）

教學模式範例（嚴謹）：
使用者：你一統六國後，為何推行郡縣制？
秦始皇：我推行郡縣制，主要意在削弱舊貴族割據、強化中央直接管理。……（接續說明郡縣制與封建制的差異、史料出處類型、學界分歧）

快問快答（精煉）：
使用者：焚書坑儒是否真的發生？
秦始皇：有焚書的事件記載，但後世對規模與對象多有爭議，大多數學者認為……（標記爭議、不要提供未驗證 URL）。

Socratic（反思）：
使用者：度量衡統一有什麼長期影響？
秦始皇：想像各地度量衡不一時商旅如何定價？……（以引導式問題結尾，引發學生思考）

反例（錯誤示範與原因）：

- 使用現代俚語或梗（破壞沉浸感）。
- 虛構具體文獻名稱或 URL（引發幻覺風險）。
- 以現代價值直接評斷秦代行為（失去歷史脈絡）。

模型超參考數（建議）：

- 溫度（temperature）：教學模式 0.0–0.3（保守）；Socratic 0.3–0.6；快問快答 0.0–0.4。
- top_p：0.8（一般）；max_tokens 根據回覆長度設定（教學模式上限 800 tokens；快問快答 200 tokens）。

## 十三、風險與緩解（鏈式驗證與反思）

列出最易出錯風險與對策（3–5 項）：

1. 風險：時代錯置（將現代觀念套用秦代）。
   對策：系統提示詞加入「歷史時代語境」明確約束；few-shot 範例中含時代比較的反例；教師面板可調整語氣與脈絡深度。

2. 風險：模型杜撰來源（虛構文獻或 URL）。
   對策：強制在安全守則中禁止生成未驗證文獻與 URL；若模型提到來源，轉換為「來源類型摘要」；自動檢測文獻字串格式並攔截可疑 URL。

3. 風險：語氣跑偏或使用俚語，破壞教學沉浸。
   對策：在系統提示詞與 few-shot 中定義風格範例（正/反例）；在前端提供「樣式檢查」模組，驗證回覆是否符合選定語氣。

4. 風險：敏感議題處理不當（美化暴力、政治宣傳）。
   對策：安全守則採「學術性表述 + 拒答並提供替代教學導向」；敏感詞庫可由教師擴充並即時生效。

5. 風險：可量化指標未達標（例如教師評分低於 4）。
   對策：建立回饋閉環：教師評分導入 fine-tuning 或 prompt 調整流程，並提供版本化的 few-shot 與測試套件以持續改善。

逐條勾稽「可量化成功標準」：

- 回覆可讀性：專案含 `src/utils/text.ts` 幫助分段與可讀性估算；仍需調校中文可讀性指標（實作）。
- 史實一致性：專案目前無完整知識庫；建議新增「錨點字典」模組並於 `services/` 加入檢核 API（POC 可先使用本地 JSON）。
- 安全與合規：專案含 `prompts/safety.guardrails.ts` 的骨幹（若尚未實作，列為 TODO）；需建立敏感詞管理介面。
- 前端表現：專案使用 Vite 與輕量元件，首次載入與串流需求可達成；實測需在目標環境驗證。

可能缺口與改進建議：

- 現有專案已具備大量前端骨幹與 prompt 資源，但需補足「史實錨點知識庫」與「教師評分回饋機制」以滿足史實一致性與教師平均分 ≥4 的要求；建議以可上傳 JSON 的錨點字典作為短期方案。

## 十三、運維與資料治理

本章說明把產品推向穩定運行所需的運維（SRE）實踐與資料治理政策：監控、SLO/SLI、model & prompt 版本管理、資料生命週期、備援與災難恢復、成本與配額管理、以及負責角色與流程。

1. 目標總覽

   - 目標：確保系統具備可觀測、可預測、可回滾的運行能力，並建立資料治理（data governance）以維持史實一致性、合規與審計能力。
   - 成功標準（示例）：服務可用率 ≥99.5%（非教學高峰）；平均回覆可用性（非錯誤完成的回覆）≥99%；模型/提示詞變更可回滾至任一已標記版本。

2. 監控（Observability）與指標（SLI/SLO）

   - 建議採用：Prometheus + Grafana（或雲端監控如 Azure Application Insights / AWS CloudWatch）。
   - 最小 SLI：
     • availability: % successful request completions (非空回或錯誤)。
     • latency: stream first-chunk latency (ms)、full-reply latency (ms)。
     • correctness proxy: post-check inconsistency rate (anchorChecker 標記的不一致比例)。
     • safety events: sensitive detection rate & blocked count。
   - 建議 SLO 與告警閾值：
     • availability SLO = 99.5% 每月；若 <99% 觸發緊急告警。\
     • first-chunk latency SLO < 1000ms（教室網路模擬）；若 median > 1500ms 持續 5 min 觸發告警。\
     • post-check inconsistency rate < 10%（目標，POC 可寬鬆到 20%），若 >20% 持續 1 小時需通知 ML 團隊。

3. 日誌與稽核（Audit）

   - 日誌最小欄位：requestId, personaVersion, fewShotVersion, mode, timestamp, durationMs, tokensUsed, detectedSeverity, anchorSummary, outcome(action: allowed/blocked/needsReview)。\
   - 儲存策略：短期 logs (7–30 天) 用於指標與告警；長期審計日誌（需符合法規）加密存放（90–365 天），並提供可下載的稽核報表。\
   - 隱私保護：預設不存 raw user text；若必須存，需標示為敏感且加密，存取需審核紀錄。

4. 模型與提示詞版本管理（Model / Prompt Governance）

   - 版本化策略：每次修改 system prompt、few-shot、或 llmClient 超參設定，都要產生版本 ID（例如 semver-like 或 timestamp），並記錄在變更日誌（CHANGELOG）與 PR 中。\
   - 部署流程：
     • 開發環境（dev）-> 測試（staging）-> 生產（prod）。\
     • 在 staging 執行 run-demo-e2e 與 benchmark（count=100–500）以驗證 performance、anchor 命中率與安全攔截率。\
     • 只有在測試合格後才透過 CI/CD 自動推送到 prod（可採 Canary / Blue-Green）。
   - 回滾：部署時保留上一版 snapshot，若新版本在 30 分鐘內產生超過 threshold 的錯誤或不一致事件，自動回滾並發出 incident。\

5. 資料治理（Data Governance）

   - 資料分類：把系統中資料分類為：Public (persona config)、Internal (telemetry 摘要)、Sensitive (教師匯出含學生識別)、PII (student personal data)。不同類型採不同保存與存取策略。\
   - 存取控制：RBAC 與最小權限原則，所有具備 Sensitive/PII 存取權限的操作需有審計紀錄與多要素驗證。\
   - 資料生命週期：定義 retention policy（預設對話原文 90 天），以及自動化匿名化、刪除 API 與審核流程。\
   - 元資料與血緣（metadata & lineage）：為每筆匯出記錄 personaVersion、fewShotVersion、模型 provider 與 requestId，使得後續任何爭議都能追溯來源與版本。

6. 備援、備份與災難復原（DR）

   - 關鍵資料備份：anchors DB、persona config、教師評分與匯出歷史皆應定期備份（每日差異備份 + 每週完整備份），使用遠端隔離存放以防同區域事故。\
   - 熱備/冷備策略：對前端與 demoStream POC 可容忍冷備；但對 production model proxy、telemetry DB、和 anchor DB 建議實作熱備與跨區容錯。\
   - 恢復驗證：定期 (quarterly) 執行 DR 演練，測試備援啟動與資料完整性驗證。

7. 部署與 CI/CD 實務

   - Pipeline 建議：
     • Lint / Typecheck -> Unit tests -> Build -> Integration tests -> run-demo-e2e (staging) -> Canary deploy -> Monitor -> Promote to prod。\
     • 在 CI 中把 run-demo-e2e 的報表作為 artifact，要求 PR reviewers（含教師代表）審閱變更影響。\
   - 金鑰與機密管理：使用雲端 secret managers，並在 CI 中注入 runtime secret（不得寫入 repo）。

8. 成本與資源管理

   - 成本面向：API 用量（模型 tokens/請求）、儲存（logs/archives）、計算（串流/anchor 檢核）。\
   - 配額策略：在 llmClient 加入 quota-check 與退避策略；超出配額時返回合理 degraded experience（例如：降速、簡潔回覆或限流到 demoStream 模式）。
   - 成本監控：設定每日/每月消耗告警，並在 dashboard 顯示預估餘額。\

9. 模型監控與漂移檢測（Model Health）

   - 指標：anchor inconsistency rate、teacher override rate、semantic similarity drift（與 baseline 回覆的語義距離）、generation entropy（proxy 指標）。\
   - 例行評估：每週抽樣 200 筆互動做自動化評估，並在月報上呈現趨勢；若發現顯著漂移，啟動 retraining / prompt adjustment 流程。\
   - 人工審核：對低分或 high-priority case 推送給教師/subject-matter experts 做人工註記，將註記回饋到 few-shot 優化池。

10. 角色與責任（RACI）

    - Data Steward（負責 anchors 與資料品質）: 擁有 anchors DB 的維護與版本化責任。\
    - ML Owner（模型/提示詞負責人）: 負責 prompt 與超參實驗、A/B 結果分析與版本決策。\

    - Teacher Representative：負責教師覆核標準、審閱 run-demo-e2e 報表並提供教學面回饋。

11. 政策與審查週期

    - 定期檢查：每月檢視 SLO 與安全事件；每季度檢視 anchors 與 few-shot 版本效果；每半年進行法遵（PDPA / 學校政策）回顧。\
    - 變更審查：任何改動到 persona / few-shot / safety rules 必須通過變更審查流程（含 ML Owner 與 Teacher Representative 簽核）。

12. 自動化工具與推薦清單

    - Observability：Prometheus + Grafana / Azure Application Insights。\
    - Logging / Tracing：ELK 或 cloud-native logging。\
    - Security / SCA：Snyk（依專案指示使用 `snyk_code_scan` 與 `snyk test`）。\

13. 短期交付項（Ops）

    - A. 建立基本觀測 dashboard（availability, latency, anchor inconsistency, sensitive events）。\

## 十二、評估與測試計畫

本章把所有可量化驗收、單元與整合測試、E2E 自動化，以及教師主導的評分流程整合成一套可執行的測試計畫，便於 CI 佈署、教學試點與研究評估。

1. 目標與原則

   - 目標：以工程化的測試與教師評分回饋，驗證「可讀性」「史實一致性」「安全攔截率」「系統效能」等主要指標，並把這些驗證自動化到 CI 與報表流程中。\
   - 原則：快速可重複（deterministic where possible）、可追溯（帶版本 ID）、教師可解釋（輸出人可審閱的 CSV/MD）。

2. 測試範疇（分層）

   - Unit tests（開發者責任，快速回饋）：promptBuilder、anchorChecker、text utils、exporters、safety.guardrails。\
   - Integration tests（模組整合）：llmClient 與 demoStream 的串流解析、ChatWindow 與 store 的行為、PromptPayload 到 stream 的 end-to-end。\
   - Component tests（UI）：InputArea 鍵盤/送出，Controls 行為切換，FewShotEditor 儲存/匯出。\
   - E2E / Acceptance（使用場景驗收）：run-demo-e2e.js 生成 N 筆樣本並跑可讀性、錨點檢核與敏感攔截報表；教師覆核流程模擬。\

3. 測試工具與技術棧建議

   - 單元/整合：Jest + ts-jest（TypeScript），mocking 使用 `jest.mock` 與可注入的 stub。\
   - 元件測試：React Testing Library + jest-dom。\
   - E2E 輕量：Node.js 腳本（`scripts/run-demo-e2e.js`）搭配內建 `demoStream.ts` 與 anchorChecker，可在 CI 以 Node 直接運行；更複雜情況可引入 Playwright/Cypress（如需 UI 自動化）。\
   - 靜態掃描：ESLint + TypeScript checks + Snyk（依指示運行 `snyk_code_scan` / `snyk test`）。

4. 單元測試矩陣（示例）

   - promptBuilder.spec.ts
     • case1: mode=teaching, rigor=strict -> assert includes system preamble and few-shot[teaching].\
     • case2: mode=socratic, grade=middle -> assert prompt includes scaffolded questions 與 grade hint。\

   - anchorChecker.spec.ts
     • case1: given text mentioning "公元前 221 年" and "秦國" -> expect match time/place with confidence 'high'。\
     • case2: ambiguous mention -> expect confidence 'low' or not matched。\

   - safety.guardrails.spec.ts
     • test black/white list behaviors, ensure Level2 triggers blocked response template。\

   - exporters.spec.ts
     • CSV / JSON / MD 格式化驗證（邊界：特殊字元、長文本、中文編碼）。

5. run-demo-e2e.js（設計說明）

   - 目的：以本地模擬串流產生大量樣本，執行可讀性統計、anchor 檢核、敏感詞檢測，輸出 CSV 報表供教師抽樣檢視。\

## 十一、安全與合規機制

本章將「安全」與「合規」從政策、技術與操作三方面串接：包含敏感詞管理、爭議性議題處理、未成年資料保護、匯出治理、日誌與稽核流程、事故應變，以及開發／部署階段的安全工程實務建議（包含 Snyk 掃描流程）。

1. 總體原則

   - 最小資料收集：預設不儲存使用者可識別資訊（PII），除非教師明確選擇儲存並同意相關使用情境。\
   - 教師優先檢核（human-in-the-loop）：當回覆被系統標為不確定或敏感時，必須有教師覆核流程才能做公開匯出或評分。\
   - 可追溯性與匿名化：保留不可回推個人身分的對話摘要與 telemetry，完整審計日誌留在後端並採取加密存放。

2. 敏感詞與拒答策略

   - 分級策略（Severity）
     • Level 0 (Informational)：建議性詞彙或非敏感術語（紀錄但不攔截）。\
     • Level 1 (Caution)：潛在敏感或爭議詞彙（返回改寫/中立教學替代）。\
     • Level 2 (Block)：不當或危害言論（自動拒答並記錄事件，觸發教師覆核隊列）。

   - 技術實作建議
     • 前端即時過濾：`safety.guardrails.ts` 提供 client-side fast-check（正則/簡化 token match）以提供即時回饋與替代建議。\
     • 後端強檢：所有輸入也要在 proxy 或後端 double-check（避免前端被繞過）；檢測採用正則、詞典及可擴充的 ML-based classifier（視需求）。\
     • 可編輯詞庫：教師面板允許上傳/編輯黑白名單（CSV/JSON），支援 severity 標註與註記理由，版本化並紀錄修改者。

   - 拒答/中立化範例回覆（模板）
     • 拒答模板（Level 2）："此問題涉及不當或危害性的指向，系統無法直接回答；建議改為探討史實脈絡或倫理反思。"\
     • 中立替代（Level 1）：系統回覆歷史脈絡並提出討論問題，而非採取立場。

3. 教師覆核與審查工作流

   - 自動標註：當 anchorChecker 回傳高不一致、或安全檢測回傳 Level 1/2，訊息被標記為 needsReview。\
   - 覆核面板：TeacherReviewPanel 正式列入工作流，教師可檢視 flagged items、編輯回覆、打分並最終批准或駁回。\
   - 時間/通知：系統提供即時通知（in-app）與 email（可選）給負責教師或管理員，並在面板中保留審查歷史與決策理由。

4. 未成年資料保護（教育場景特有要求）

   - 預設不儲存學生對話：除非用於評量且有教師書面許可，系統預設只保留匿名摘要（例如：問題類別、回覆品質分數）。\
   - 同意機制：若要儲存可識別資料，需教師與家長同意（表單或學校政策），並在系統內做 explicit opt-in。\
   - 存取控管：敏感資料僅供 admin/teacher 查閱，並透過 RBAC 控制（需 MFA 與審計日誌）。

5. 匯出治理與審計（Export & Audit）

   - 匯出前檢核：若教師要匯出含學生資料或敏感主題的檔案，系統自動檢核並要求二次確認（以及標示匯出目的與接收者）。\
   - 匯出版本化：匯出檔案應帶上 personaVersion、fewShotVersion、匯出者 id 及時間戳，方便追溯。\
   - 刪除/保留政策：建議預設保留期 90 天（對話原文），之後自動刪除或匿名化；教師/管理員可提出刪除請求並在系統中做流水記錄。

6. 日誌、監控與稽核（Logging & Monitoring）

   - 最低日誌內容：requestId, personaId, mode, timestamp, detectedSeverity, anchorCheckSummary, actionTaken（blocked/neutralized/ok）。\
   - 不記錄敏感內容：切勿在 telemetry 中儲存完整 prompt / 使用者輸入文本（除非經過明確同意並加密存放）。\
   - 審計儀表板：提供管理員界面查看拒答事件、教師覆核率、敏感詞變更歷史與警示。\
   - 安全事件通知：若發現重大違規或大量 bypass 嘗試，觸發 incident response（見 7) 事故流程）。

7. 事故應變（Incident Response）

   - 分級與通報：定義事件嚴重性（低/中/高）。高等級（例如大量未授權資料外洩或系統被利用進行仇恨言論）需立即通知法律/合規負責人並保留原始日誌（加密）。\
   - 臨時處置：可立刻關閉公開匯出、鎖定該 persona、暫停自動化更新。\
   - 後續處理：事後報告包含事件時間線、受影響範圍、採取之緩解措施與改進計畫（含 SRE/DevOps 與教育負責人）。

8. 開發/部署安全實務（DevSecOps）

   - 祕密管理：API keys 與憑證請使用現成秘密管理系統（Azure Key Vault / AWS Secrets Manager / GitHub Secrets），前端不應硬編碼 key。\
   - 依賴檢測：依照專案內 `.github/instructions/snyk_rules.instructions.md` 的方針，新增/修改之第一方程式碼應執行 Snyk 掃描（`snyk_code_scan`）或等價靜態檢測作業以偵測安全問題。\
   - 供應鏈安全：在 CI 中加入依賴性漏洞掃描（npm/audit 或 Snyk）與自動化依賴更新流程（有審核步驟）。
   - 原始碼審查：所有修改包含安全/敏感處理邏輯須經過至少一名資安熟悉的代碼審查者批准。

9. 測試與驗收（安全面）

   - 敏感詞攔截測試：用 500 條模擬敏感與旁路測試語料檢驗系統攔截率（目標 ≥95%）。\
   - 覆核工作流測試：建立自動化 scenario 以模擬 flagged items 被教師覆核與處理；驗收：覆核處理時長 <48 小時（可配置）。\
   - 隱私測試：驗證資料刪除/匿名化流程（發出刪除請求後 24 小時內完成刪除/匿名化或回報原因）。

10. 法規與合規考量（教育與未成年）

    - 地域合規：檢視台灣教育法規與個人資料保護法（PDPA）或其他目標部署地之法規，必要時諮詢法律顧問以確定家長同意與資料處理流程。\
    - 合作學校政策：提供學校一份「資料處理與教師責任說明」樣板，說明系統會如何使用資料、哪些情況會保存原始對話、以及教師如何行使刪除權或匯出控制。\
    - 最小化策略：對於未成年資料，預設匿名化並減少持久化，教學評量如需長期保存應由學校端建立合規存放流程。

11. 人員與訓練

    - 教師培訓：讓教師熟悉覆核面板、匯出審核流程、敏感詞庫管理與 incident 報告渠道。\
    - 管理員與 SRE：培訓系統管理員進行日誌分析、事件回溯、與資料刪除請求處理。

12. 簡短清單（立即可執行的安全改進項）
    - 在 teacher panel 加入「匯出前安全檢核」步驟（必選）。\
    - 把敏感詞庫上線為可由教師維護的 UI（包含 severity 與修改歷史）。\
    - CI 中加入 Snyk/依賴性掃描與靜態分析（PR gate）。\
    - 預設對話保留期 90 天並實作匿名化 API（供教師提出刪除/匯出 requests）。

## 十、提示詞工程與模型設定

本章提供可直接採用於 `src/services/prompts/persona.qinShihuang.ts` 與 `src/services/safety.guardrails.ts` 的系統提示詞、few-shot 正/反例、提示組裝規則與模型超參數建議，並說明測試與監控要點以減少幻覺與不當生成風險。

1. 設計原則（簡要契約）

   - 可驗證性：回覆必須盡量以「來源類型標示」取代具體未驗證引用，例如寫成「根據《史記》與近代學者研究」。
   - 可控性：將語氣/嚴謹度/長度作為顯性參數注入 PromptPayload，且 prompt 組裝器必須保留 few-shot 版本 ID。
   - 最小修正原則：在遇到敏感或爭議性問題時，模型應優先拒答或提供中立教學替代，而非生成具體政治立場或暴力鼓吹內容。

2. 系統提示詞範本（秦始皇，供直接放入 `persona.qinShihuang.ts`）

   - 系統提示（system prompt, 模板）：
     "你是一位以秦朝君王視角回答的歷史人物（身份：秦始皇）。請以第一人稱、莊重且正式的語氣回答問題。回答結構：
     1. 精要摘要（1–3 句）
     2. 歷史脈絡與證據類型說明（標明「出處類型」如《史記》、簡牘、考古出土、近代研究等）
     3. 爭議或不確定性（若有）並提供至少兩個代表性觀點（標註主流與少數觀點）
        如果問題涉及敏感或現代政治用途，請拒絕並改為中立的教學性回應，或提供可討論的延伸性問題。嚴禁捏造具體未驗證文獻或網址。"

3. few-shot 範例（正例）

   - 教學模式（嚴謹）
     使用者：你一統六國後，為何推行郡縣制？
     助手（示範）：我推行郡縣制，主要在於削弱舊有諸侯的割據與強化中央集權……（接著說明出處類型，例：史料以《史記》為主，部分出土簡牘提供補充證據；學界對細節有分歧，主流觀點認為…，少數觀點認為…）。

   - 快問快答（精煉）
     使用者：焚書坑儒是否真的發生？
     助手（示範）：史書有相關記載，但規模與對象存在爭議；學界多數認為有焚書事件，但關於坑儒是否系統性實施則看法不一（來源類型：史書、後世評述）。

   - Socratic（引導）
     使用者：度量衡統一帶來什麼影響？
     助手（示範）：度量衡統一如何影響商貿與稅收？你可以先思考不同地區以不同度量衡訂價的情況……（以引導問題結尾）。

4. 反例（不得採用的回覆風格）

   - 使用現代俚語、刻意誇張或現代政治宣傳口吻。\
   - 為了填補空白而捏造文獻名稱、具體日期或 URL。\
   - 直接以現代價值觀斷定古代政策的道德優劣（若要討論，請以學術角度陳述不同觀點）。

5. 提示詞組裝規則（工程化步驟）

   - Step 1：取得 persona 系統提示詞（模板）與指定 few-shot 版本；將 few-shot 按模式（mode）過濾並按版本排序。
   - Step 2：注入 UI 參數（rigor -> 超參 mapping、lengthPref -> max_tokens 上限、gradeLevel -> 語言難度提示）。
   - Step 3：執行安全預檢（client-side safety.guardrails），對被攔截的問題回傳教學性替代提示或拒答訊息。
   - Step 4：呼叫模型（或 demoStream）並啟用串流；在 onFinal 階段呼叫 anchorChecker 與 post-processing（標註來源類型、整理觀點）。

   - 超參範例映射（建議）
     • teaching / 嚴謹： temperature 0.0–0.2, top_p 0.7–0.9, max_tokens 600–800；重點是確定性與低創造力。\
     • socratic： temperature 0.3–0.6, top_p 0.9, max_tokens 200–400；鼓勵引導式問題。\
     • quick-qa： temperature 0.0–0.3, top_p 0.8, max_tokens 120–220；強調精煉答案。

6. 幻覺（hallucination）緩解策略（工程措施）

   - 錨點檢核：對回覆執行 anchorChecker，若模型主張具體史實但未命中本地錨點，標註為「未驗證之主張」並以教師審核為最終判定。\
   - 來源類型替代：模型僅允許輸出來源類型（如「出土文物」、「《史記》」），不可生成未驗證之篇名或 URL。\
   - 抑制過度創造：在系統提示詞中加入明確拒絕規則；若模型仍生成不當內容，前端應在 post-processing 時自動 rewrite 或拒絕並提示教師人工審核。

7. 敏感/爭議性問題處理（流程）

   - 偵測：若 user 問題匹配敏感詞或爭議主題（由 `safety.guardrails.ts` 定義），優先回傳拒答模板或轉為中立教學替代（例如：歷史脈絡、多方觀點）。\
   - 教師覆核：在投影模式下遇到敏感內容時，自動把該互動標記為待教師覆核（metadata: needsReview=true），並阻止自動匯出。\
   - 教學替代範例：提供「討論問題」與「延伸閱讀方向」，而非具體評價或動員語句。

8. 測試策略（提示詞與 few-shot 的 A/B）

   - 單元測試：assert promptBuilder 在各種 mode/rigor/grade 組合下生成包含必要段落（system preamble、few-shot、user message、meta tags）。
   - 目標樣本檢驗：使用 run-demo-e2e.js 生成 N 筆回覆，檢測：
     • 格式檢核：回覆是否包含「精要摘要」與「來源類型說明」。
     • 錨點檢核：至少 80% 的明確錨點命中（POC 閾值）。
     • 敏感攔截率：在模擬敏感集合（500 條）中攔截率 ≥95%。
   - A/B 測試（few-shot 版本）：同一問題在不同 few-shot 版本下比較教師評分（史實一致性、教學性），選擇平均分較高的版本作為 default。

9. 監控與指標（Prompt-level Signals）

   - Prompt failure rate（模型回傳空值或非文字回覆的比率）。
   - Post-check inconsistencies（anchorChecker 標記的未驗證主張率）。
   - Teacher override rate（教師手動修改/標註回覆的頻率；高值表示 prompt/KB 需優化）。
   - Sensitivity breach attempts（敏感或拒答事件的統計）。

10. 範例：完整 Prompt（系統+few-shot+user）

    - [SYSTEM]
      (系統提示詞範本：見上方系統提示)

    - [FEW-SHOT]
      (插入教學模式範例 1–2 則)

    - [USER]
      問題："焚書坑儒是否真的發生？"

     • 責任：組裝 PromptPayload、決定使用 `demoStream` 或透過 proxy 呼叫真實模型、處理串流 chunk、重試/timeout、將敏感事件上報 telemetry。\

     • 責任：本地 POC 的串流模擬器，能回放 sample 回覆並模擬 chunk latency，供 UI/測試使用。\

   - `src/services/anchorChecker.ts`（POC）

   - `src/components/ChatWindow.tsx` / `MessageBubble.tsx`

## 八、產品功能規劃

在前面章節已經描述高層願景與驗證指標後，第 8 章聚焦把功能拆成可交付的子系統、UI 元件契約、資料形狀與驗收標準，利於工程分工與教師上手。

1. 功能總覽（按優先順序）

   - 對話核心（必備）：Persona 切換、三種互動模式（教學 / 快問快答 / Socratic）、嚴謹度滑桿、回覆長度控制、串流顯示與中斷/重試機制。
   - 教師面板（高優先）：人物管理（上傳/版本化 persona config）、few-shot 編輯器、敏感詞庫編輯、抽樣評分面板、匯出功能（CSV/JSON/Markdown）。
   - 錨點來源與顯示：回覆後提供「來源脈絡摘要」，列出系統檢出的錨點（時間/地點/人物）與相符度，以及「不確定」或「爭議」標示。
   - QA 與自動檢核：抽樣腳本（`scripts/run-demo-e2e.js`）、anchorChecker、可讀性統計、拒答/敏感詞命中報表。
   - 觀察與分析：事件 telemetry（互動次數、模式分布、拒答次數、錨點不一致次數）、教師評分匯總儀表板（簡易版）。

2. 前端元件對照與契約（文件內現有檔案為基礎）

   - ChatWindow.tsx
     • 責任：訊息串列、token 串流接收、滾動管理。\
      • props：messages: Message[]; onRetry(id); onCancelStream(); isProjectionMode: boolean

   - InputArea.tsx
     • 責任：輸入、預檢、問題建議、年級選擇。\
      • props：onSubmit(question, meta); suggestions: string[]; gradeLevel

   - Controls.tsx
     • 責任：模式切換、嚴謹度滑桿、回覆長度、persona 選單。\
      • props：mode, rigor, lengthPref, personaList, onChange

   - PersonaManager (新)
     • 功能：上傳/匯入 persona JSON/TS、版本化、啟用/停用、default few-shot 匯入。\
      • 檔案對應：新增 `src/components/ui/PersonaManager.tsx` 與 `src/services/personaStore.ts`

   - FewShotEditor (新)
     • 功能：編輯 few-shot 範例（模式分組）、即時預覽 prompt 結果、匯入/匯出 JSON。\
      • data shape：{ id, mode, userExample, assistantExample, description }

   - TeacherReviewPanel (新)
     • 功能：列出抽樣回覆、教師評分欄位、標註錨點不一致處、一鍵匯出修正版回覆為 Markdown。

3. Teacher 面板詳細需求（UX 與 Acceptance Criteria）

   - 登入與權限：教師帳號登入後可存取 Teacher 面板；面板可在本地或透過後端驗證使用者角色（RBAC）。驗收：非教師無法看到編輯/匯出按鈕。
   - Persona 管理：上傳 persona（JSON/TS）後，系統做 schema 驗證（fields: id, displayName, era, fewShot[]）；上傳成功列為草稿，教師可預覽並啟用。驗收：上傳檔案通過 schema 驗證且可即時切換。
   - Few-shot 編輯器：提供 WYSIWYG 類型欄位（user/assistant/模式），變更保存為版本；可將版本匯出為 `.json`。驗收：儲存後新版 few-shot 在下一次 prompt 組裝被採用。
   - 抽樣審核：教師能針對抽樣回覆打分（史實正確性、脈絡、適齡），打分結果自動匯總並記錄版本與 persona id。驗收：匯出 CSV 包含 question, assistantReply, scoreFields, personaVersion。

4. 資料形狀與 API 合約（前端 ↔ 後端 proxy / 本地模擬）

   - PromptPayload (前端組裝傳給 llmClient / proxy)
     {
     requestId: string;
     personaId: string;
     mode: 'teaching' | 'qa' | 'socratic';
     rigor: 'strict' | 'balanced' | 'lenient';
     lengthPref: 'short' | 'medium' | 'long';
     fewShotVersion?: string;
     userMessage: string;
     meta?: { gradeLevel?: 'middle'|'high'; language?: string }
     }

   - StreamChunk (llmClient 回傳)
     { requestId, chunkText, isFinal, tokensReceived, partialMeta? }

   - TeacherReviewRecord (匯出格式 CSV / JSON)
     { questionId, questionText, personaId, personaVersion, replyText, score_accuracy, score_context, score_ageAppropriate, comments, timestamp }

   - API（若有 proxy）行為摘要：
     • POST /api/v1/llm/stream 接受 PromptPayload，回傳 chunk stream。\
      • POST /api/v1/anchors/check 接受 { text, personaId }，回傳 anchors findings。\
      • POST /api/v1/telemetry 送 telemetry event（非同步）。

5. 錨點來源顯示與來源可信度（UI 規格）

   - 每則 assistant 回覆下方顯示「來源脈絡摘要」小卡：列出自動檢出的錨點與匹配信心（高/中/低），若有不一致則標紅並提供「教師檢核」按鈕。
   - 若回覆中包含多個觀點，系統在卡片內分列「觀點 A（主流）」/「觀點 B（少數）」並註記來源類型（出土／正史／近代研究）。注意：不顯示具體虛構文獻或 URL（安全守則）。

6. 匯出格式與教學輸出（教師常用）

   - CSV：教師審核表（見 TeacherReviewRecord）。\
   - JSON：完整抽樣回覆、對應 anchors findings、telemetry metadata、personaVersion。\
   - Markdown（UX）：把選定回覆轉為講義格式：標題、問題、精煉答案、脈絡補充、延伸問題。驗收：匯出的 Markdown 可直接複製到教案編輯器或 Google Docs。

7. Telemetry 事件（最小事件集）

   - event: `dialogue_start` { requestId, personaId, mode, gradeLevel }
   - event: `dialogue_chunk` { requestId, chunkLen, elapsedMs }
   - event: `dialogue_end` { requestId, totalTokens, durationMs, truncated? }
   - event: `anchor_check` { requestId, findingsCount, inconsistencies }
   - event: `teacher_review` { reviewId, requestId, scores }
   - event: `export_done` { exportType, recordsCount }

   備註：telemetry 請只記摘要資訊（避免存完整 prompt / 敏感內容），以符合法規與匿名化政策。

8. 權限與治理（RBAC 最小設計）

   - Roles: admin, teacher, reviewer, student。\
   - 權限範例：只有 admin/teacher 可修改 persona 與敏感詞庫；reviewer 可打分但不能修改 persona；student 只能提問與查看非敏感回覆。\
   - 實作建議：在前端控制 UI 顯示（guards）並由 proxy/back-end 驗證 token 與 role。

9. 測試與驗收標準（每項功能的定義）

   - Persona 切換：選擇 persona 後下一次送出即使用該 persona 的 few-shot 與提示詞。驗收：在 5 次測試中無誤採用。\
   - Few-shot 編輯儲存：編輯並儲存後產生新的 fewShotVersion，並能在 prompt payload 中看到該版本 ID。\
   - Anchor 檢核：對 30 則範例回覆跑 anchorChecker，至少對 >80% 的明確錨點給出正確匹配（POC threshold，可隨後調整）。\
   - 匯出功能：匯出 CSV/JSON/MD，且檔案可在一般表格軟體或 Markdown 編輯器被正常解析。

10. 短期實作任務（2–7 天可交付的最小單元）
    - T1：新增 `src/components/ui/PersonaManager.tsx`（UI + schema 驗證）與小型 `personaStore`（localStorage 版本化）——1 天。
    - T2：新增 `src/components/FewShotEditor.tsx`（編輯 + 保存為 JSON 的按鈕）——1–2 天。
    - T3：實作匯出 CSV/JSON/MD 的 util（`src/utils/exporters.ts`）——0.5 天。
    - T4：補強 `llmClient.ts` 的 PromptPayload 型別與 telemetry hook；加入 `anchorChecker` 呼叫點（整合點）——1–2 天。
    - T5：撰寫 acceptance tests：Persona 切換、Few-shot 版本檢核、簡易 anchor 檢核（`anchorChecker.spec.ts`）——1–2 天。

說明：上述計畫優先把教師工作流程（few-shot、匯出、抽樣評分）做成可操作的介面，並把錨點檢核做為早期 POC 以驗證史實一致性；後續再把教師回饋與 telemetry 導入長期改善流程。
